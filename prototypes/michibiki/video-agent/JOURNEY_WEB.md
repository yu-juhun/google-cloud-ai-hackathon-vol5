# 最終レポートから旅全体の動画を作る

PR #20の追加実装。設計判断は `docs/wiki/concepts/michibiki-video-verification.md` を参照。
既存の一体験・8秒APIは互換用に残し、画面の主導線を旅程動画へ変更した。

## 導線

- 最終レポートの動画セクションで「この旅を動画にしたい」を選ぶ。
- 参照画像と旅程の利用に同意し、「この旅の動画を作る」を押す。
- 旅程の最大4地点を訪問順に映像化する。4場面なら約24秒。短い旅程は場面数に応じて短くなる。
- 完成した動画を同じセクションで再生する。
- 履歴から過去の旅を開くと、同じ最終レポートから生成・再生できる。

既存の地図・体験談と静的動画プレビューは維持する。履歴内に別の生成画面は増やさない。

## API・保存

- `POST /api/journey-videos`: `mission_id`, `feedback`（任意）, `consent`。
- `GET /api/journey-videos/by-mission/{mission_id}`: 状態、完成場面数、動画URL、参照写真の出典。
- どちらも既存の `X-Michibiki-Client` で所有者を確認。
- DBマイグレーション5で `journey_video_jobs` を追加する。既存のレポート・一体験動画は消さない。
- 入力スナップショット、場面計画、Veo操作名、生成状態、各場面と完成動画の保存先を保持。
- Storageの `videos/journeys/{job_id}/` に参照画像・場面動画・完成動画を非公開で保存。
- 動画サービスはそのプレフィックスに限定した読み込み・新規作成権限を使う。
- 完成動画は既存のバックエンド署名URLで配信。期限切れ後は保存先から再発行。

## 生成と編集

保存済み旅程から採用地点を選び、全場面で同じ人物参照を使う。人物は保存済みアバターを優先し、
なければサーバー設定のデモ画像を使う。元のアップロード写真を新たに保存する処理は追加しない。

乃木坂のレビュー済み4地点では、place IDと対応付けたCommons写真を取得する。許可するライセンスは
CC0・Public domain・CC BYのみ。未知の地点を似た施設写真へ自動で置き換えない。
対応する実景写真がない場合は、その地点の生成済み体験画像、または場所名・予定活動からの仮想描写。
Google Maps写真を動画の生成素材として流用しない。全地点の実景写真自動検索は未実装。

Veo 3.1で各場面8秒を生成し、複数場面では冒頭1.5秒ずつを編集対象外にする。
0.6秒の短い暗転、音のクロスフェード・音量調整、地名と仮想体験表示をFFmpegで追加する。
この固定編集は毎回の映像品質を保証するものではなく、人物・場所・切替の確認が必要。

## 再読み込み・失敗時

キューや新しいサービスは追加しない。画面が状態を取得するときに、場面の開始・回収・編集を進める。
画面を閉じた間も開始済みのVeo操作はGoogle側で進むが、次の場面の開始は再訪時まで一時停止する。
途中状態はDBに残るので、同じ旅を開き直して続きから確認できる。

同時ポーリングはDBの期限付き排他で調整し、取得後の古い状態で二重送信しない。
Veoの受付結果が不明な場合は自動再送せず停止する。生成済み操作の状態取得と編集は再試行できる。
安全性フィルターによる失敗を、静的動画で成功扱いにはしない。

## 確認状況

コード確認：バックエンド74件・動画18件のチェック、フロントビルド成功。
個人GCPへデプロイ済み。Web画面と同じAPIからVeoの4場面生成・保存を実行し、
24.3秒・720p・24fps・H.264/AACの完成動画を生成した。
初回の編集ではLinux FFmpegのフレームレートエラーが発生したため、同じLinux環境で再現し、
時刻調整後と各フェード後に24fpsを明示して修正した。保存済み4場面は再生成していない。

署名URLによる動画取得、Rangeリクエスト206、同じ動画ジョブの再取得、履歴一覧から同じ
最終レポートを取得するAPIの動作を確認した。編集再開から取得まで46.1秒だったが、これは
Veo生成時間を含まない復旧確認であり、通常の全体平均ではない。画面の3〜6分は4場面の推定目安。
参照写真はこの検証では1場面で取得、3場面は場所・活動からの仮想描写にフォールバックした。
全場面で実景写真が取得できた検証としては扱わない。

ブラウザ自動操作の接続が利用できないため、実際のクリック操作と動画の連続視聴は未確認。
審査用ブラウザで、最終レポートと履歴の両方から確認する。
