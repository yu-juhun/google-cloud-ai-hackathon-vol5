# ペルソナ・インテイクエージェント v2設計: アバター進化 + 関係性スキーマ

## 目的

`docs/superpowers/specs/2026-09-13-persona-intake-agent-design.md`(以下「v1 spec」)で実装した
ペルソナ・インテイクエージェント(Tasks 1-10、`agent/persona-intake`ブランチで実装済み)を拡張する。
v1では「静止画2枚の口パク」「固定`priority`(high/medium/low)」だったアバター表現とペルソナ
スキーマを、以下の2点で高度化する:

1. **アバターが会話を通じて「パートナー」として認識されるよう、見た目が進化する体験を提供する**
2. **ペルソナ属性を、固定ドメインの枠組みの中で、ユーザーごとに相対的な重要度を持つ
   「関係性情報」として整理し、他エージェントとの連携をしやすくする**

v1 specの前提(インテイク専用・推薦は行わない・多言語対応スコープ外等)は変更しない。

## 背景・検証の経緯

本specの内容は、以下の実機検証を経て確定した(詳細はブレインストーミングの会話ログを参照):

- **アバター描画方式**: Gemini 2.5 Flash Image(Nano Banana)による属性ベースの見た目編集を
  実際にAPI呼び出しで検証済み。同一キャラクターの一貫性を保ったまま(顔・服・背景を変えずに)
  車椅子の追加、口の形の変更ができることを確認した
- **リアルタイムの「話している」表現**: 当初は音声のviseme(口の形)を周波数解析で複数分類し
  高精度なリップシンクを目指したが(v1〜v5の反復検証)、簡易な音声解析ではviseme分類の精度に
  限界があり、種類を増やすほど逆に不自然になることが判明した。最終的に「口の開閉2状態のみを、
  非対称な減衰速度(開くのは中速・閉じるのはゆっくり)でクロスフェードし、常時の呼吸モーションを
  加える」方式に落ち着いた
- **Veo 3.1(動画生成)**: 参照画像を使ったリップシンク動画生成は実際に動作したが、
  (1)動画の長さが8秒固定、(2)生成に約98秒かかる、(3)生成済み音声を後から別の音声(Gemini Live APIの
  リアルタイム音声)に差し替える手段がない、という3つの制約により、リアルタイム会話用途には
  採用しないと判断した
- **Gemini Omni**: 「音声入力に応じた映像生成」を持つが、Vertex AIから直接呼び出すと
  `gemini-omni-flash-preview is only supported in the Interactions API and cannot be called
  directly` というエラーが返り、現時点では一般開発者向けAPIとして利用できないことを確認した
- **中村さんのagent(michibiki)のUI参考**: 移動条件を車椅子種類・幅・段差・連続移動時間・
  同行者タイプ・確認したい設備のチェックリストという形でフォーム化していた。これは本エージェントの
  自由記述`description`フィールドで十分カバー可能と判断し、スキーマ変更は行わない
  (詳細な項目の連携は統合方針が決まる後日のミーティングで協議する)

## スコープ

- **対象**: v1 specで実装済みの`persona-agent-backend`/`persona-agent-frontend`への追加変更
- **対象外(v1と同様)**: 推薦機能、多言語対応、ペルソナの永続化、他エージェントとの実際の
  API連携(スキーマの形だけ整える。実際の受け渡し方式は統合方針が決まる後日のミーティングで決定)

## アーキテクチャ

### 会話フローへの追加ステップ

v1 specの会話フロー(音声対話→終了→ペルソナ抽出→キーワード推論)に、
**アバター画像生成**を1ステップ追加する。会話中(finish前)には一切画像生成を行わない
(レイテンシ・コストを抑えるため、会話完了時に1回のみ実行する):

```
1-5. (v1 specと同じ: 音声対話 → 終了トリガー → ペルソナ抽出 → キーワード推論)
6. アバター画像生成(新規): ベースアバター画像 + 確定したペルソナ属性(domain/category/
   description)を Gemini 2.5 Flash Image に渡し、「同じキャラクターの見た目を保ったまま、
   属性を反映した見た目に編集して」と指示する。1回のAPI呼び出しで全属性をまとめて反映する
   (属性ごとに逐次呼び出さない — API呼び出し数を抑える)
7. 完成したペルソナJSON + 更新後のアバター画像(base64)を、WebSocket接続上でメッセージとして
   フロントエンドへ送信する
```

**ベースアバター画像の扱い**: 会話開始時にフロントエンドが表示する初期アバター画像は、
事前に1回生成して`persona-agent-frontend/public/`に静的ファイルとして配置する
(会話ごとに毎回生成しない)。ステップ6の編集は、この静的なベース画像を入力として使う。

### リアルタイムの「話している」表現(フロントエンド側、変更)

v1 specのAvatarPanelは音量に応じて口の開閉2枚を単純に切り替えていたが、以下に変更する:

- 口を閉じた画像・開いた画像の2枚を**同一DOM位置に重ねて配置**し、`opacity`を音量に応じて
  連続的に変化させる(離散的な切り替えではなく、なめらかなクロスフェード)
- 音量から目標値(0-1)を計算し、現在値をその目標値へイージングで近づける。**上昇(口が開く)は
  中程度の速さ、下降(口が閉じる)はゆっくり**という非対称なレート(実際の口の筋肉の動きに近い)
  を使う
- アバター全体に、常時ループする微細な「呼吸」アニメーション(わずかな拡大縮小+上下移動、
  4〜5秒周期)を別レイヤーとして重ねる。これにより会話していない時間帯も完全に静止しない

viseme(口の形)を3種類以上に増やす高精度なリップシンクは、検証の結果不採用とする。

## ペルソナJSONスキーマの変更

v1 specの`Attribute`型を以下に変更する:

```json
{
  "persona_id": "string (UUID)",
  "raw_summary": "string",
  "attributes": [
    {
      "domain": "mobility | dietary | purpose | companions | language | background | other",
      "category": "string — 自由記述(v1と同様、固定enumにしない)",
      "description": "string — 自由文",
      "rank": "integer — 1始まりの一意な順位。1が最重要。全attributes内で重複しない",
      "confidence": "high | medium | low",
      "inferred_keywords": ["string", "..."]
    }
  ]
}
```

**変更点**:
- **`domain`(新規、固定7値)**: `mobility`(移動制約)/ `dietary`(食事)/ `purpose`(目的)/
  `companions`(同行者・人数)/ `language`(言語対応)/ `background`(居住地・出身地・国籍等)/
  `other`(上記に当てはまらないもの)。実際の音声テストで抽出された属性
  (居住地・出身地・言語希望・食事目的・食事の好み・同行者・人数)がすべてこの7分類でカバー
  できることを確認済み
- **`priority`(廃止)→`rank`(新規)**: 従来は各attributeが独立に`high/medium/low`を持っていたが、
  これを**全attributesを通じた一意な整数順位**に置き換える。「このユーザーには言語対応が
  食事の好みより重要」という属性間の相対比較を明示的に表現する。ペルソナ抽出時の同じGemini
  呼び出し内で、全属性を見た上でrankも同時に出力させる(追加のAPI呼び出しは発生させない)

`category`は引き続き固定enumにしない(v1 specの制約を継続)。`domain`は固定するが、その中の
具体的な内容(`category`/`description`)は自由記述のままとする。

## テスト方針

- `persona_extraction.py`: 固定のトランスクリプトを入力に、`domain`が7値のいずれかであること、
  `rank`が1から始まる連番でattributes数と一致すること(重複なし)をユニットテストで検証する
  (Gemini呼び出しはモック)
- アバター画像生成関数: Gemini画像生成呼び出しをモックし、入力(ベース画像+属性リスト)から
  正しいプロンプトが構築されることを検証する(実際の画像内容の一貫性は自動テスト不可 — 手動確認)
- フロントエンドのクロスフェード・呼吸モーション: 既存のVitestでは音声解析ロジック
  (目標値計算・非対称イージング)を関数として切り出し、入力音量に対する出力opacityの
  数値を検証する。CSSアニメーション自体の見た目は手動確認とする

## オープンな論点

- ベースアバター画像の生成タイミング(初回起動時に自動生成 or 事前に1枚だけ手動生成して
  コミットしておくか)は、実装時に決定する
- `domain`の7分類は、統合方針が決まる後日のミーティングで、他メンバーのエージェント
  (松野さん・中村さん・白井さんのコンセプト)との連携要件が明確になった時点で見直す可能性がある
- 中村さんのagent(michibiki)が使っている車椅子の詳細項目(種類・幅・段差・連続移動時間)の
  構造化は、今回は`description`の自由文に委ねる。より厳密な連携が必要になった場合は、
  `mobility`ドメインのみサブフィールドを追加する形で拡張する(他ドメインには影響しない)
