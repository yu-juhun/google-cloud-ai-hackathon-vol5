# ペルソナ・インテイクエージェント 設計(劉さん個人コンセプト・フェーズ2)

## 目的

`docs/wiki/concepts/steering.md`のフェーズ2「個別コンセプト」における劉さんの担当を実装する。
本エージェントは**推薦を行わない**。ユーザーと音声で対話し、移動制約・食事制約・目的・家族構成・
優先事項などの「ペルソナ」を動的に抽出し、他のメンバーが作る推薦エージェント(松野さん・中村さん・
白井さんのコンセプト)が利用できる構造化データとして返す、**インテイク(受付)専用のエージェント**である。

## 背景・非目標

- フェーズ1(ミニハッカソン、車椅子×バリアフリー飲食店)は参考情報として`steering.md`に残るが、
  本specの前提としない
- 統合方針(どのコンセプトを最終的に採用・結合するか)は未確定。本specは劉さん個人の担当範囲
  (個人ブランチでの先行開発)のみを対象とし、他メンバーのエージェントとの実際の連携は範囲外
- 出力するペルソナJSONの永続化(DB保存等)は今回のスコープ外。APIレスポンスとして返すのみ

## ユーザー像(想定)

3人家族の父親(大人の代表として意思決定・対話する)。イスラム教徒の車椅子ユーザー。
移動制約(車椅子)・食事制約(ハラール等)・家族同伴という複数の属性を持つが、
**属性は固定リストで決め打ちしない** — 対話の中で本人が語ることから動的に抽出する。

## 全体アーキテクチャ

```
┌─────────────────────────────────────────────────────────────────┐
│ persona-agent-frontend (Cloud Run, React + Vite)                  │
│  - マイク入力キャプチャ → WebSocketでバックエンドへ音声ストリーム送信      │
│  - 静的アバター画像 + 受信音声の音量に応じた簡易口パクアニメーション        │
│  - 「完了」ボタン → 会話終了トリガーをバックエンドへ送信                  │
│  - 完了後、抽出されたペルソナJSONを画面に表示                          │
└─────────────────────────────────────────────────────────────────┘
                              │ WebSocket (音声ストリーム)
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│ persona-agent-backend (Cloud Run, Python + FastAPI)                │
│                                                                   │
│  1. WebSocketエンドポイント: ブラウザからの音声をGemini Live APIへ中継  │
│     (APIキーはバックエンドのみが保持)                                │
│  2. 会話終了トリガー受信 → Live APIセッションを終了                    │
│  3. ペルソナ抽出: 会話履歴全体を1回のGemini呼び出しで構造化              │
│     (attributes配列 + raw_summary)                                │
│  4. キーワード推論: 抽出済みattributes全体を1回のGemini呼び出しで      │
│     まとめて処理し、各attributeにinferred_keywordsを付与              │
│  5. 最終的なペルソナJSONを、同じWebSocket接続上でJSONメッセージとして返す │
└─────────────────────────────────────────────────────────────────┘
                              │ Gemini Live API (音声、ステップ1-2)
                              │ Gemini API (テキスト、ステップ3-4)
                              ▼
                         Google Cloud (Vertex AI)
```

**必須GCP要件との対応**: 実行系 = Cloud Run(2サービス)、AI系 = Gemini(Live API + テキスト生成)。
このエージェント単体でもコンテストの必須要件(実行系1つ以上+AI系1つ以上)を満たす。

## コンポーネント詳細

### persona-agent-frontend

- React + Vite(既存`frontend/`と同じ技術スタック、ただし別リポジトリディレクトリ・別Cloud Runサービス)
- 画面構成: アバター表示エリア、マイクON/OFFボタン、字幕表示(音声内容のテキスト表示、
  デバッグ・アクセシビリティ両方に有用)、「完了」ボタン、完了後のペルソナJSON表示エリア
- マイク音声はブラウザの`MediaRecorder`/`AudioContext`でキャプチャし、WebSocket経由で
  バックエンドへストリーミング送信する
- アバターの口パクは、バックエンドから受信した音声データの音量(RMS等)を見て、一定閾値を
  超えたら「開いた口」画像、それ以下なら「閉じた口」画像を切り替えるだけの簡易実装とする
  (リップシンクや表情変化は今回のスコープ外)

### persona-agent-backend

- Python + FastAPI(既存`backend-api`/各agentと同じ技術スタック)
- **WebSocketエンドポイント** (`/ws/converse`): ブラウザ ⇄ バックエンド ⇄ Gemini Live APIの
  中継を行う。Gemini Live APIとの接続はサーバーサイドのSDK(`google-genai`)を使う
- **会話終了**: フロントエンドから終了メッセージを受信したら、Live APIセッションを閉じ、
  それまでの会話履歴(音声から変換されたテキストのトランスクリプト。Live APIは音声と同時に
  テキスト形式のトランスクリプトも返せるため、それを蓄積して使う)を確定する
- **ペルソナ抽出関数**: 蓄積したトランスクリプト全体を1つのプロンプトでGemini(テキスト生成、
  Live APIとは別の通常のGemini呼び出し)に渡し、下記スキーマのJSONを生成させる
  (`response_mime_type: application/json`でJSON強制)
- **キーワード推論関数**: 抽出された`attributes`配列全体を1回のプロンプトで渡し、
  各attributeに対応する`inferred_keywords`をまとめて生成させる(attributeごとに逐次呼び出す
  のではなく、1回のバッチ呼び出しでAPI呼び出し数を抑える)

## ペルソナJSONスキーマ

```json
{
  "persona_id": "string (UUID)",
  "raw_summary": "string — 対話全体を要約した自由文。他エージェントが構造化データを解釈しにくい場合の保険",
  "attributes": [
    {
      "category": "string — 自由記述。固定enumにしない(例: mobility, dietary, family, purpose, preference等、対話内容に応じて自由)",
      "description": "string — 自由文。例: '車椅子の横幅は63cm、電動'",
      "priority": "high | medium | low — 本人がどれだけ重視しているか(対話のトーン・繰り返しから推定)",
      "confidence": "high | medium | low — 会話からどれだけ確信を持って抽出できたか",
      "inferred_keywords": ["string", "..."]
    }
  ]
}
```

**制約**:
- `attributes`は0件以上(対話が短く何も抽出できなかった場合は空配列。エラーにはしない)
- `category`に値の制約はないが、抽出プロンプト内で「一貫した命名を心がける」ことをGeminiに
  指示する(同じ会話内で"mobility"と"移動"のような表記揺れが起きないようにする程度の緩い制御)

## 会話フロー(詳細)

1. ユーザーがマイクボタンを押す → フロントエンドがWebSocket接続を開始
2. バックエンドがGemini Live APIセッションを開始。システムプロンプトで
   「あなたは旅行・外食のプランニングを手伝うアシスタントです。ユーザーの移動の制約、
   食事の制約、今日の目的、同行者、優先したいことを自然な会話で聞き出してください。
   一度に多くの質問をせず、相手の話を踏まえて掘り下げてください」等を設定する
3. ユーザーが話す → 音声がバックエンド経由でLive APIへ送信 → Live APIが音声で応答
   (バックエンドはフロントエンドへ音声を中継、同時にトランスクリプトを蓄積)
4. ユーザーが「完了」ボタンを押す → フロントエンドが終了信号を送信
5. バックエンドがLive APIセッションを終了し、ペルソナ抽出 → キーワード推論を順に実行
6. 完成したペルソナJSONを、同じWebSocket接続上でメッセージとしてフロントエンドへ送信する。
   フロントエンドが画面に表示する(このメッセージ受信後、WebSocket接続を閉じてよい)

## デプロイ・開発方針

- チームの合意(`steering.md`「進め方(フェーズ2)」)に従い、**劉さんの個人ブランチ**
  (例: `agent/persona-intake`)で作業する
- 検証は劉さんの**個人GCPプロジェクト**で行う(共有プロジェクト`project-3bcd6d36-2338-4b32-848`
  には影響を与えない)
- リポジトリ内の配置: `persona-agent-backend/`, `persona-agent-frontend/`
  (既存の`backend-api/`, `frontend/`と並ぶ、フラットなトップレベルディレクトリ)
- 共用ドキュメント(`docs/wiki/`)への影響は最小限にする。今回のspec自体は
  `docs/superpowers/specs/`に置き、`docs/wiki/`は変更しない
  (統合方針が決まった時点で、必要であれば`docs/wiki/concepts/`に決定事項として記録する)

## テスト方針

- `persona-agent-backend`: ペルソナ抽出関数・キーワード推論関数は、固定のトランスクリプト
  テキストを入力としたユニットテストで検証する(Gemini呼び出し自体はモックし、
  プロンプト構築とレスポンスのパース処理を検証する)
- WebSocket中継部分は、Live API自体をモックしたテストは複雑になるため、
  実際のGemini Live APIキーを使った手動での動作確認(スモークテスト)を基本とする
- `persona-agent-frontend`: 既存`frontend/`と同様にVitestでコンポーネント単体テストを行う
  (マイクAPI・WebSocketはモック)

## オープンな論点

- Live APIのシステムプロンプトの具体的な文言・対話のトーンは、実装しながら調整する
  (今回のspecでは方向性のみ規定)
- ペルソナJSONの他エージェントへの実際の受け渡し方式(API直接呼び出し、共有ストレージ等)は、
  統合方針が決まる後日のミーティングで決定する
- 多言語対応(英語・アラビア語等)は今回のスコープ外。日本語での対話を前提とする
