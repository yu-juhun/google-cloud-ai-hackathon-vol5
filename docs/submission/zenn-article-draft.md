## 第5回のルールで押さえること

- 記事を出すかどうかは任意。出す場合は**カテゴリを「Idea」**にして、**記事のURLをプロジェクトに登録**する
- **提出したあとは直せない**
- 審査では、提出物のすべてを細かく見るとは限らない → **大事なことは記事の冒頭に置く**
- テーマは「『作れる』から『使える』へ」。「使えるエージェント」とは、自律的に動きながら、**ガバナンスとセキュリティを意識して設計された**エージェントのこと
- FAQ:「**自分たちで開発した部分**と、**外部のサービスをそのまま使っている部分**」が分かる構成説明が求められている

## 課題:行ってみないと分からない

車いすユーザーにとって、出かける前の下調べは欠かせません。でも、ネットで分かる情報には限りがあります。

- 「バリアフリー対応」と書いてあっても、**入口の段差や通路の幅など、実際に通れるかどうか**までは分からない
- 車いすの幅や、越えられる段差の高さは**人によって違う**ので、同じ情報でも行ける人と行けない人がいる
- 結局「行ってみないと分からない」ので、外出そのものをあきらめてしまうことがある

【要確認:出典のある数字を1つ入れる(例:車いすユーザーの人数、外出時に困った経験の割合など)】

## michibiki とは

michibiki は、**ユーザーの体と移動の条件を受け取った「AIの分身」が、行き先を先に下見してくれる**旅行支援エージェントです。

キャッチコピーは「行きたい一日を、先に確かめる。」です。

### 使い方

1. **写真からアバターを作る**:顔写真をアップロードすると、YouCam API で自分のアバターが作られます
2. **声で条件と希望を伝える**:AI と音声で会話しながら、車いすの幅、越えられる段差、食事の制約、行きたい場所などを伝えます(例:車いすの幅 70cm、段差は 2cm まで)
3. **分身が先に下見に行く**:条件を受け取った分身エージェント【要確認:何体か】が、それぞれ行き先を調べます。地点ごとに、通路の幅・段差・混み具合などを確認します
4. **体験を画像と動画で受け取る**:分身が「行ってみた」結果を、体験レポートと画像で受け取れます。さらに Veo で短い体験動画も作れます
5. **履歴を見返す**:過去の下見の結果は、履歴ページからいつでも確認できます

## エージェントの設計

michibiki では、複数のエージェントが役割を分け、自分で判断しながら動きます。

- **聞き取りエージェント**:AI が自分から質問し、会話の中からユーザーの条件を聞き出します。聞き出した条件は、ほかのエージェントが使える形(persona JSON)にまとめます。条件にはそれぞれ、優先順位と確からしさ(confidence)が付きます
- **分身エージェント**:受け取った条件をもとに、自分で行き先を調べ、ユーザーが通れるかどうかを確かめます【要確認:情報源と調べ方の流れ】
- **動画エージェント**:体験レポートとアバターから、短い体験動画を作ります

ポイントは、**ユーザーが一つずつ指示しなくても、条件を伝えるだけで下見が進むこと**です。

## 安心して任せられる設計

第5回のテーマは「『作れる』から『使える』へ」です。自律的に動くエージェントを安心して使ってもらうために、michibiki には次の仕組みを入れています。

### 指示の紛れ込みを防ぐ

- ユーザーからのフィードバックは「データ」として扱い、「指示」としては読まないように、AI への指示文の中で区別しています
- フィードバックが体験レポートと関係あるかを、Gemini が先に判定します。関係ない内容は、動画生成に回しません
- 判定がうまくいかなかったときは、安全のため「生成しない」側に倒します
- 【要確認:分身がWebページを読むときの対策があれば追記】

### 個人の情報を守る

- アバターの見た目に反映するのは、**移動に関する情報だけ**です(許可した項目以外は反映しない仕組み)。食事の制約など、ほかの個人的な情報は見た目には出しません
- 動画を作る前に、本人のデータか、同意があるか、同じ依頼が重複していないかを確認します
- 作った動画は、期限付きのURL(署名付きURL)で配信します

### 何が起きたかを後から確認できる

- 下見や動画生成の進み具合を画面に表示し、結果は履歴として残ります【要確認:Cloud Logging なども使っていれば追記】
